# Changelog

All notable changes to Hybrid Cache for Amazon S3 from 3.0.0 onward are documented in
this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Releases before 3.0.0

Every release up to and including 2.8.4 is in the [pre-3.0.0 changelog](changelog-pre-v3.md),
which is closed. Look there for the history of any 0.x, 1.x or 2.x release.

## [3.0.5] - 2026-11-11

3.0.5 lets the proxy connect to an origin's IPv6 addresses on every path, adds `connection_pool.dns_ip_strategy` to choose which address families it looks up, and refuses passthrough and `CONNECT` destinations that lead back to a proxy. It also retries a GET or HEAD whose upstream connect fails, and part and range requests that waited on another request's fetch no longer get `504`.

**Upgrade impact:** Operators whose DNS64 resolver uses the local-use NAT64 range `64:ff9b:1::/48`, whose clients connect through the proxy to one of its own addresses, or who tuned `connection_pool.ip_failure_threshold` should read [Upgrading to 3.0.5](docs/UPGRADING.md#upgrading-to-305) before upgrading.

### Fixed

- Previously, a GET or HEAD that IP distribution (on by default) sent to an origin's IPv6 address failed before connecting, and now connects. This affected an origin with only IPv6 addresses in public 1.7.7 to 3.0.4, and a dualstack origin in public 1.15.2 to 3.0.4, where the proxy tried IPv6 addresses first. Thanks to [@samantha-earthmover](https://github.com/samantha-earthmover) for [GitHub issue #18](https://github.com/aws-samples/sample-s3-hybrid-cache/issues/18).
- Previously, in public 1.10.0 to 3.0.4, a `CONNECT` request naming a bracketed IPv6 address, such as `CONNECT [2001:db8::1]:443`, failed, because the proxy looked the bracketed text up as a host name. The destination policy now checks the address itself.
- Previously, in public 1.16.0 to 3.0.4, the destination policy allowed a NAT64 address that embeds a prohibited IPv4 address, such as `64:ff9b::a9fe:a9fe` for the instance metadata address. It now judges an address in `64:ff9b::/96` by the IPv4 address it embeds, and refuses all of the local-use range `64:ff9b:1::/48`. See [Destination policy](docs/ARCHITECTURE.md#destination-policy-ssrf-protection).
- Previously, in every public release up to 3.0.4, a GET or HEAD whose connection to the origin could not be opened got `502` at once, except a signed range GET, which retried twice. It is now retried like other connection errors, up to three times, each time on the next address when IP distribution is on. A signed range GET runs that retry up to three times, so it can make up to 12 attempts; see [Connection pooling](docs/CONNECTION_POOLING.md#6-error-recovery).
- A key whose cache rule turns hedging on follows different connect-retry rules; see [Hedging](docs/HEDGING.md#connection-diversity).
- Previously, in public 1.9.0 to 3.0.4, a failed connect counted twice against its address when IP distribution was on. At the default `ip_failure_threshold` of 3, the address left rotation after 2 failed connects. It now counts once, so the address leaves after 3.

### Changed

- The HTTPS passthrough (port 443) and `CONNECT` tunnels on the TLS proxy listener (port 3129) now try each address the destination policy allows, in the order DNS returns them, until one connects. Previously they tried only the first, so a dualstack destination failed on a host with no IPv6 route. Each attempt has 10 seconds and the whole connect 30, where a `CONNECT` attempt had only the operating system's limit.
- The HTTPS passthrough and `CONNECT` tunnels now refuse a destination when any address they would connect to leads back to a proxy. Such an address is on the proxy host's interfaces, is loopback or unspecified, or is listed in the new `server.tls.tunnel_refused_addresses`, even when `endpoint_overrides` lists it. The passthrough closes the connection and `CONNECT` answers `403`.
- Uploads and other writes now count a failed connect against the address, as reads do, so an address that keeps failing leaves rotation for both. A successful connect for a write resets the address's count.
- A part or range request that waited on another request's fetch through all `download_coordination.max_waiter_resubscriptions` rejoins now fetches from S3 itself, as a full-object GET does, instead of getting `504`.
- A dashboard log request (`/api/logs`) now reads at most the eight newest application log files, where it could read every file in the directory, newest first, until it had enough entries.

### Added

- `connection_pool.dns_ip_strategy` chooses which address families the proxy looks up and which it tries first. The default, `ipv6_and_ipv4`, keeps the previous order; set `ipv4_only` on a host with no IPv6 route or `ipv6_only` on a host that reaches the origin only over IPv6. See [Address families](docs/CONFIGURATION.md#address-families).
- `server.tls.tunnel_refused_addresses` (default empty) lists addresses that lead back to a proxy without being on its interfaces, such as each proxy's EC2 public IPv4 or Elastic IP address. The HTTPS passthrough and `CONNECT` tunnels refuse them. See [TLS proxy listener configuration](docs/CONFIGURATION.md#tls-proxy-listener-configuration).

## [3.0.4] - 2026-11-10

3.0.4 stops write cache reclamation from removing unread uploads it does not need to, recovers on its own from a torn `.pending` line or damaged shard checkpoint, and keeps completed multipart uploads for `put_ttl`.

**Upgrade impact:** Operators who cache multipart uploads, read the write cache figures on `/metrics` or OTLP, or upgrade a fleet from 3.0.3 one proxy at a time should read [Upgrading to 3.0.4](docs/UPGRADING.md#upgrading-to-304) before upgrading.

### Fixed

- Previously, in public 3.0.0 to 3.0.3, a write cache reclamation pass could remove more unread uploads for bytes the previous pass had already freed, when that pass's recomputation could not re-read a shard. This affected proxies that report `write_cache.staged_authority_epoch` `1`. Each proxy now records on the cache volume what it removes from each shard, and every proxy subtracts it until that shard is recomputed.
- Previously, in public 3.0.0 to 3.0.3, an object read for the first time, deleted or replaced stayed in the staged figure until its shard was next recomputed. A reclamation pass sized meanwhile could remove more unread uploads than it needed to, on proxies that report `write_cache.staged_authority_epoch` `1`. The removal now leaves the figure within one `consolidation_interval`, and at once on the proxy that made it.
- Previously, a completed multipart upload stayed in the write cache for a day, whatever `put_ttl` said. It now stays for the key's `put_ttl`, as a single-part upload does, so with the default `1h` an unread one leaves after an hour; entries already cached keep their expiry. Thanks to [@cameronbraid](https://github.com/cameronbraid) for [GitHub PR #28](https://github.com/aws-samples/sample-s3-hybrid-cache/pull/28).
- Previously, a blank or torn line in a proxy's `.pending` file, its record of recent uploads, stopped the staged figure until an operator removed the line. The proxy now moves such a line to `{instance}.pending.torn` at its next periodic recomputation and counts it in `write_cache.pending_lines_quarantined_total`. Another proxy does the same for a stopped proxy's file after a grace period of 15 minutes to 24 hours.
- Previously, a shard checkpoint that did not parse kept the staged figure unknown. The proxy now keeps its bytes in `{XX}.json.torn` and replaces it by recomputing that shard. A checkpoint that cannot be read, or that a newer release wrote, is left in place.
- Previously, at `write_cache.staged_authority_epoch` `1`, a full validation scan reported the bytes graduated since the last scan as write cache drift, in `cache_size.accounting_drift` and as a log warning. It now marks that figure not evaluable, with reason `staged_authority_epoch_1`, and both validation log lines say which figures they compared. Thanks to [@cameronbraid](https://github.com/cameronbraid) for [GitHub issue #29](https://github.com/aws-samples/sample-s3-hybrid-cache/issues/29).

### Changed

- The decisions that need the staged figure now share one recomputation in each proxy, which reads shard checkpoints 64 at a time, and a metrics collection reads them once. `write_cache.staged_authority_snapshot_recomputes_total` counts recomputations rather than reads, and `write_cache.staged_authority_snapshot_age_secs` can exceed 5 s by a recomputation's read time.
- A metrics collection that has not returned after twice `metrics.collection_interval`, or 60 s if that is longer, now logs an error, and OTLP then records the figures a `/metrics` request reads.
- At `write_cache.staged_authority_epoch` `0`, `write_cache.staging_figure_unknown_seconds` and its error log now also report a staged figure the proxy cannot recompute, although reclamation then sizes itself from the event-maintained counter.
- At `write_cache.staged_authority_epoch` `1`, the warning that `write_cache.resident_bytes` is over its bound is no longer logged before the proxy has recomputed its first staged figure.

### Added

- `write_cache.staged_removal_debit_bytes` shows the staged bytes subtracted for removals that their shards' figures do not yet include. See [Coordination across proxies](docs/EVICTION.md#coordination-across-proxies).
- `write_cache.pending_lines_quarantined_total` counts the lines moved from a `.pending` file to its `.pending.torn` file.

## [3.0.3] - 2026-11-09

3.0.3 stops write cache cleanup from deleting uploads that nobody has read, corrects the `write_cache.inflight_bytes` figure, and adds a gauge that shows when cleanup cannot work out how much to remove.

### Fixed

- Previously, in public 3.0.0 to 3.0.2, a write cache cleanup pass could delete far more than it needed to. If a pending-credit file stayed locked for more than 100 ms, the pass fell back to a counter that overstates how much is staged, and it removed unread uploads until it reached its target. This affected proxies that report `write_cache.staged_authority_epoch` `1`. On one contributor's proxy, 12 passes in 90 minutes removed 67,894 unread uploads (127.9 GB) while about 100 GB was staged against a 1,135 GB trigger. A pass now works out the staged size again after it takes the eviction lock, and removes nothing by size if it cannot. See [Which computation is in force](docs/EVICTION.md#which-computation-is-in-force). Thanks to [@akash-polybee](https://github.com/akash-polybee) for [GitHub PR #27](https://github.com/aws-samples/sample-s3-hybrid-cache/pull/27).
- Previously, in public 2.7.0 to 3.0.2, `write_cache.inflight_bytes` could read lower than the uploads in flight, even `0`, after a cleanup pass, and the proxy logged a write cache capacity underflow warning. It now counts only the uploads in flight.

### Changed

- When a proxy cannot work out the staged size again, `/metrics` and the check that starts a cleanup pass now use the last size it did work out, however old. Before it has worked one out, `/metrics` shows the counter.

### Added

- `write_cache.staging_figure_unknown_seconds` on `/metrics` and OTLP shows how long a proxy has been unable to work out the staged size. It reads `0` while the proxy can. `write_cache.staging_figure_unknown_passes_total` counts the cleanup passes that removed nothing by size for that reason. If the size stays unknown for 60 s, the proxy logs an error, at most once every 10 minutes. [When the staged size cannot be read](docs/EVICTION.md#which-computation-is-in-force) explains what limits staged bytes in the meantime, where to set an alert on the gauge, and what to do.

## [3.0.2] - 2026-11-07

3.0.2 bounds every wait on the origin during an upload, answers upstream timeouts with `504`, and drops the cached copy of an object when a write's outcome is unknown. It fixes a multipart race that could cache a part body S3 did not keep, and counts `get_ttl` from when data was fetched. At `get_ttl: "0s"`, a GET whose `If-Match` names the cached ETag is now revalidated with S3 and served from the cache. It removes S3 Select support, which was incomplete: a SelectObjectContent request now gets `501 NotImplemented`. It also hardens how the proxy handles malformed requests and what it writes to its logs, and with an allowlist set it connects only to addresses the destination policy accepts. Five `/metrics` fields that always read `0`, and the library crate's exports that the binary does not use, are removed.

**Upgrade impact:** Operators who set `server.tls.connect_allowlist` and resolve S3 to private addresses through `connection_pool.dns_servers`, and operators whose clients use S3 Select, should read [Upgrading to 3.0.2](docs/UPGRADING.md#upgrading-to-302) before upgrading. So should operators whose dashboards or alarms read the removed `/metrics` fields, and developers whose code uses the `s3_proxy` library crate.

### Added

- `connection_pool.upstream_write_idle_timeout` (default `120s`) sets how long the origin of an upload, multipart operation or copy may go without moving a byte before the proxy answers `504`. See [Upstream write timeout](docs/CONFIGURATION.md#upstream-write-timeout).

### Fixed

- An upload, multipart operation or copy whose origin stopped responding held its connection and request slot until the client gave up (3.0.1 and earlier). The proxy now answers `504 Gateway Timeout` after `connection_pool.connection_timeout` while connecting, or after `upstream_write_idle_timeout` with no bytes moving. A transfer that keeps moving is never cut off.
- Some upstream timeouts were answered `502` or `500`, including a GET or HEAD whose first-byte retries ran out (3.0.1 and earlier). Upstream timeouts are now answered `504 Gateway Timeout`, as documented, except that a request that waited on another request's fetch at `get_ttl: "0s"` gets `502` when its own revalidation does not complete. See [Error statuses the proxy sends itself](docs/ERROR_HANDLING.md#error-statuses-the-proxy-sends-itself).
- When S3's answer to a write, such as a CompleteMultipartUpload, copy or DeleteObjects result, was cut short or passed 100 MiB, the proxy could return it as a complete `200` (3.0.1 and earlier). It now answers `502 Bad Gateway` for an answer cut short or larger than 8 MiB, and drops the key's cached copy.
- S3's answers to writes were held in memory without being counted against `server.max_inflight_buffer_bytes` (3.0.1 and earlier). They are now counted, and never refused once the request has been sent, so `inflight_memory.reserved_bytes` can exceed `ceiling_bytes` while they are held. See [In-flight memory ceiling](docs/CONFIGURATION.md#in-flight-memory-ceiling).
- After a write timed out or lost its connection once its whole request was sent, the proxy kept serving its cached copy, although S3 may have applied the write (3.0.1 and earlier). For a PUT, copy, CompleteMultipartUpload or DELETE, signed or presigned, the proxy now drops the cached copy before it answers, as it already did for DeleteObjects. See [Writes the origin stops answering](docs/ERROR_HANDLING.md#10-writes-the-origin-stops-answering).
- A full-object GET or HEAD waiting on another request's fetch of the same object was answered `504` after about 120 seconds when that fetch took longer (public 1.16.0 to 3.0.1). A large object on a slow link could hit it. The waiting request now fetches from S3 itself.
- A lookup of an origin's name held a lock that every cache miss and new upstream connection needs, so one slow or failing lookup stalled all origin traffic on that proxy (public 1.9.8 to 3.0.1). Lookups now run outside it, are bounded at 10 seconds, and a failed lookup of a new name is remembered for `connection_pool.dns_refresh_interval`. See [Failed lookups](docs/CONFIGURATION.md#failed-lookups).
- The connection keepalive settings and `tcp_recv_buffer_size` did not apply to the connections that carry uploads (3.0.1 and earlier). They now apply to every upstream connection, as documented.
- A quiet proxy wrote its buffered access-log records only when another request arrived (3.0.1 and earlier). It now writes them every `logging.access_log_flush_interval` while idle.
- A PUT whose cache store was dropped because its temporary file had been replaced was counted as `superseded` in `signed_put.skipped_puts_total` (public 3.0.1). It is now counted as `temporary_replaced`. See [Metrics reference](docs/METRICS_REFERENCE.md#skipped_puts_total).
- If a client sent one part number twice at once with different bodies of equal compressed length, the proxy could cache the body S3 did not keep (public 3.0.0 to 3.0.1; earlier ones not examined). Revalidation with S3 did not detect it. The proxy now checks that each part file it publishes is the one the part's record describes, and otherwise caches nothing for the upload. See [Affected releases](SECURITY.md#affected-releases).
- Freshness counted from consolidation, not from the fetch, so cached data could be served up to one `consolidation_interval` past `get_ttl`, or up to 5 minutes after a backlog or a restart (3.0.1, and possibly earlier releases). With page widening on, a page not yet consolidated was served past `get_ttl` as well. `get_ttl` now counts from the fetch on both paths, so entries expire slightly sooner and S3 sees a few more `304` revalidations.
- At `get_ttl: "0s"`, a GET whose only conditional header was an `If-Match` naming the cached ETag, as split downloads send on every part, was relayed to S3, which sent the body (public 3.0.0 to 3.0.1). Such a GET, including `If-Match: *` and a list that contains the cached ETag, is now revalidated with S3 and served from the cache after a `304`. A HEAD, a weak ETag, a list without the cached ETag and another version's ETag are still relayed as sent. See [GitHub PR #26](https://github.com/aws-samples/sample-s3-hybrid-cache/pull/26), by [@samirotiv-polybee](https://github.com/samirotiv-polybee).
- An AbortMultipartUpload sent right after an UploadPart's answer could leave the upload's staging directory under `mpus_in_progress/`, counted against the in-progress multipart limit, until the incomplete-upload sweep removed it after `cache.incomplete_upload_ttl` (public 2.1.0 to 3.0.1). The Abort now moves the directory aside before removing it, and a part whose cache copy is still being written is discarded. An UploadPart that arrives after the Abort can still leave staging for the sweep; see [What reaps abandoned staging](docs/MULTIPART_UPLOAD.md#what-reaps-abandoned-staging).
- When a client disconnected after sending a whole PUT, copy, CompleteMultipartUpload or DELETE and before S3 answered, the proxy could keep serving its cached copy from before the write, although S3 had applied it (3.0.1 and earlier). A CompleteMultipartUpload or a large copy could hit this whenever the client's read timeout was shorter than S3's processing time. The proxy now finishes the write and drops the cached copy whether or not the client is still connected, as it already did for DeleteObjects and browser form uploads.
- A request with `Cache-Control: no-cache` or `Pragma: no-cache` stored its response in the cache even when a cache rule, or `cache.read_cache_enabled: false`, turned read caching off for that object (public 1.5.0 to 3.0.1). Such a request is now forwarded and streamed without storing anything.
- A browser form upload (a `POST` to the bucket) that the client interrupted before it finished dropped the cached copy of the object it named, although S3 had stored nothing (public 3.0.0 to 3.0.1). The cached copy now stays until S3 may have stored the upload.

### Security

- A request whose `Host` header is not a host name or address with an optional port, such as one holding a space or a double quote, is now answered `400`, in forward-proxy mode too.
- Access-log fields that carry request text (`bucket_owner`, `bucket`, `request_uri`, `referer`, `user_agent` and `host_header`) now escape a double quote and a backslash, so each record keeps its field count. A referer or user agent holding a backslash is written differently from 3.0.1. See [Escaping and redaction](docs/ACCESS_LOG_FORMAT.md#escaping-and-redaction).
- Presigned URL credentials are now masked in every application log line at every level, and again in the dashboard's log viewer, which also covers log files an earlier release wrote.
- A malformed CompleteMultipartUpload body is now forwarded to S3 and answered as S3 answers it, where the proxy previously closed the client's connection.
- With `server.tls.connect_allowlist` set, the HTTP forwarding paths now connect only to addresses the destination policy accepts. See [Destination policy](docs/ARCHITECTURE.md#destination-policy-ssrf-protection).
- The dashboard now logs a rejected query value escaped, so a value cannot add a line to the application log.
- The proxy no longer keeps a counter for every bucket name a request names, which let requests naming many bucket names grow its memory without bound. The counters were never exported.
- Bumped `tokio` to 1.54.1 (RUSTSEC-2026-0386) and `anyhow` to 1.0.104 (RUSTSEC-2026-0190).

### Removed

- S3 Select support was incomplete and has been removed. Through 3.0.1 the proxy could return a Select result cut short, past about 100 MiB or when S3 closed early, as if it were complete. A SelectObjectContent request is now answered `501 NotImplemented` before it reaches S3 or the cache, so send S3 Select requests to S3 directly. See [Upgrading to 3.0.2](docs/UPGRADING.md#upgrading-to-302).
- The `s3_proxy` library crate exports only what the `s3-proxy` binary uses. Public types and functions the binary never called are removed, and most others are now private to the crate. Among the removed are the methods that could store a whole object in the RAM cache under its plain cache key, where it could answer another object's range. See [Upgrading to 3.0.2](docs/UPGRADING.md#upgrading-to-302).
- Five `/metrics` fields that read `0` on every proxy are removed: `cache.cache_etag_mismatches_total`, `cache.cache_range_invalidations_total`, `cache.cache_etag_validations_total`, `cache.cache_orphaned_ranges_cleaned_total` and `cache.cache_cleanup_failures_total`, with the OTLP series `cache.etag_mismatches_total` and `cache.range_invalidations_total`. See [Upgrading to 3.0.2](docs/UPGRADING.md#upgrading-to-302).

## [3.0.1] - 2026-11-03

3.0.1 lowers the memory that consolidation and streamed cache hits hold, and lets cache hits that revalidate with S3 run concurrently. It also closes cases where a read could return one object version's bytes under another version's ETag and headers. 3.0.0's line "Range, part and conditional reads never mix bytes of two versions" did not hold in those cases. Each needed an object overwritten in place outside the proxy, except an error reply that a 2.x release cached as object data. By default, 3.0.1 fetches from S3 again any cached range that records no file identity, which includes every range a 2.x release cached.

**Upgrade impact:** Operators whose cache volume a 2.x release wrote to, and operators running several proxies on one cache volume, should read [Upgrading to 3.0.1](docs/UPGRADING.md#upgrading-to-301) before upgrading.

### Added

- To keep a cache volume that a 2.x release populated warm after upgrading, set `cache.trust_unverified_ranges: true` (default `false`), which serves ranges that record no file identity as 3.0.0 did. Use it only where objects are never overwritten in place outside the proxy. See [Ranges with no file identity](docs/CONFIGURATION.md#ranges-with-no-file-identity).
- `atomic_metadata.unverified_ranges_refused` counts ranges refused, discarded or left uncached for want of a file identity, and `atomic_metadata.retired_fill_files_unlinked` the range files deleted with them, so you can watch such a cache volume re-warm on `/metrics` or OTLP. See [Metrics reference](docs/METRICS_REFERENCE.md#atomic_metadata).

### Fixed

- Consolidation read the whole journal once per cache key and held up to 32 copies at once, so a proxy restarted over a large journal was killed for memory on every restart. Each key's consolidation now reads only that key's journal lines. On a contributor's proxy with 4 vCPU and 32 GiB, a 723 MiB journal held it at 23.6 GiB resident with no client traffic. See [GitHub PR #23](https://github.com/aws-samples/sample-s3-hybrid-cache/pull/23), by [@samirotiv-polybee](https://github.com/samirotiv-polybee).
- A streamed cache hit of one whole cached range used 1 MiB chunks and two queues of four, so a hit with a slow client held about 12.4 MiB, as a contributor measured. Every streamed hit now reads 512 KiB chunks into one queue of four, so with 16 stalled clients reading a 32 MiB cached object each hit holds about 3.9 MiB. On one m6in.2xlarge proxy with an Amazon EFS (Elastic throughput) cache volume, streamed-hit throughput is level with or above 3.0.0's in every case measured except one. With 16 concurrent GETs of a 512 MiB object it is 2.7% lower (2,750 against 2,827 MB/s). See [GitHub PR #24](https://github.com/aws-samples/sample-s3-hybrid-cache/pull/24), by [@samirotiv-polybee](https://github.com/samirotiv-polybee).
- Each cache hit that revalidated with S3, as every hit does at `get_ttl: 0`, took a proxy-wide write lock, so every other cache read waited behind it. These hits now run concurrently. In a contributor's load test against a local S3-compatible store that added 200 ms to each response, the median time to response headers at 64 clients fell from 411 ms to 214 ms. See [GitHub PR #25](https://github.com/aws-samples/sample-s3-hybrid-cache/pull/25), by [@samirotiv-polybee](https://github.com/samirotiv-polybee).
- A range file damaged on the cache volume, such as by a flipped bit, could be streamed as a complete response (public 1.8.2 to 3.0.0). A streamed response that reaches the end of a cached range now ends short if the file fails its checksum. See [Damaged range files](SECURITY.md#damaged-range-files).
- If two fills of one range ran at once during an overwrite in place outside the proxy, a read could return one version's bytes under the other's ETag (public 1.6.7 to 3.0.0). Each fill now writes its own temporary file, and a fill for an object with no cached metadata discards its copy instead of replacing a range file modified in the last 10 minutes. See [Cache integrity](SECURITY.md#cache-integrity).
- After an overwrite in place outside the proxy, a `?partNumber=` GET could return bytes cut at the other version's part boundaries, with that version's part count (public 1.6.7 to 3.0.0). A part's layout is now recorded only when its ETag matches the cached object's. See [Cache integrity](SECURITY.md#cache-integrity).
- During a rolling upgrade from 2.x, or while 2.x journal entries remained on the cache volume, a read of an object overwritten in place outside the proxy could return another version's bytes (public 3.0.0). Consolidation now discards journal entries that list a range but record no file identity, which every 2.x release writes. See [Cache integrity](SECURITY.md#cache-integrity).
- A range with no file identity, such as every range a 2.x release cached or last rewrote, was served without checking its version (public 1.6.7 to 3.0.0). It could hold another version's bytes after an overwrite in place outside the proxy, or an error reply that public 1.9.7 to 2.8.4 cached, which 3.0.0 served unless it was an S3 XML error reply. By default such a range is now refused and fetched from S3 once. See [Cache integrity](SECURITY.md#cache-integrity).
- Where public 1.9.7 to 2.8.4 had built an object's cached metadata from an S3 error reply, 3.0.0 fetched the object from S3 on every GET (public 3.0.0). That lasted until a HEAD, an eviction or a write through the proxy; the first read now removes the metadata, so the object is cached again. See [Cache integrity](SECURITY.md#cache-integrity).
- With `cache.ram_cache_enabled: true`, the RAM cache kept serving wrong bytes from one of the cases above after the cache volume's copy was corrected (public 3.0.0). A RAM copy is now served only while the cache volume's metadata still lists a range covering it. See [Cache integrity](SECURITY.md#cache-integrity).
- With `cache.ram_cache_enabled: true`, a client could upload an LZ4 frame as `{key}:range:{start}:{end}` and read it back through one proxy (public 1.6.7 to 3.0.0). That proxy then served the frame's decoded content as bytes `start` to `end` of object `{key}`. The RAM cache now holds ranges only. See [Cache integrity](SECURITY.md#cache-integrity).
- When the cached metadata named the version S3 holds now over an older version's file, each revalidation got `304` and renewed the entry, so `get_ttl` never ended it (public 1.6.7 to 3.0.0). Consolidation now keeps a listing only when the range file is the one the listing names. See [Cache integrity](SECURITY.md#cache-integrity).

## [3.0.0] - 2026-10-21

3.0.0 lets a fleet of proxies share one large cache on Amazon EFS, Amazon FSx or NFS and keeps that cache correct and within its size limit:

- Every proxy on the cache volume takes part in eviction, and eviction finds what to remove without reading every object's metadata.
- Cache size figures are recomputed from the cache's own metadata, so they correct themselves.
- Every proxy on the cache volume serves an acknowledged write: the proxy that took it at once, and the others within 1 second for object data and 5 seconds for HEAD answers by default. See [Cache freshness](docs/CACHE_FRESHNESS.md#ram-tier-coherency-contract).
- When the cache volume is slow, full or briefly unavailable, requests keep flowing: writes reach S3 uncached and reads are fetched from S3 until the volume recovers.
- The proxy answers as S3 would for the version it has cached. Range, part and conditional reads never mix bytes of two versions, conditional requests get S3's answer. Objects cached on write keep the headers they were written with, entries are revalidated as `get_ttl` says, and a damaged range in the cache is fetched from S3 again.
- Correctly signed requests that failed through the proxy for some clients now succeed, among them presigned URLs that sign extra headers, ranged SDK downloads, and virtual-hosted requests for bucket names that contain dots.
- A fleet on any 2.8 release upgrades in place. Where objects are overwritten in place, upgrade every proxy in one pass, because until all run 3.0.0 a proxy still on 2.8 can keep serving the previous version of an overwritten object. Where each object is written once, upgrade one proxy at a time.

**Upgrade impact:** Every operator should read [Upgrading to 3.0.0](docs/UPGRADING.md#upgrading-to-300) before upgrading.

### Added

- Fleet-wide eviction. The proxy holding the eviction lock writes a work list and every proxy on the cache volume deletes part of it. While a proxy older than 3.0.0 is active, or the fleet has been idle for an hour, the lock holder deletes alone. The `eviction_worklist` metrics show which mode is running. See [Eviction](docs/EVICTION.md#which-proxy-deletes).
- Orphan cleanup, which removes range files no metadata references, such as those left by interrupted writes, once every active proxy on the volume runs 3.0.0. It keeps recently written files and parts of multipart uploads still in progress. See [Shared storage](docs/SHARED_STORAGE.md#orphan-recovery).
- A node-local record of pending invalidations under `logging.local_state_dir`. A write whose invalidation the cache volume could not take is retried until it lands, across an outage or a restart. See [Caching](docs/CACHING.md#write-through-ordering).
- `s3-proxy bench-metadata`, which measures the cache volume's metadata read rate so you can size a fleet before relying on it. See [Sizing the metadata rate](docs/SHARED_STORAGE.md#sizing-the-metadata-rate).
- `/metrics` fields and OTLP series for eviction pace, size-figure drift, the write cache and orphan cleanup, and a Staged Write Tier dashboard card. `cache.eviction_backlog_projected_bytes` is the headroom figure eviction acts on; alarm on it. See [Metrics reference](docs/METRICS_REFERENCE.md#eviction-rate-admission-rate-and-whether-eviction-is-keeping-pace), [OTLP metrics](docs/OTLP_METRICS.md#staged-write-tier) and [Dashboard](docs/DASHBOARD.md#staged-write-tier).
- A `Via` header on forwarded requests. A request that loops back to the fleet, for example through a `Host` that resolves to the proxies, is answered `508 Loop Detected`. See [Error handling](docs/ERROR_HANDLING.md#9-request-loops-via-and-508-loop-detected).
- Detection of two proxies using one hostname on a cache volume, such as replicas given one fixed container hostname. Each proxy logs an error naming both identities and counts the collision in `cache.hostname_collisions_total`. A proxy whose hostname and process ID are both shared forwards uploads to S3 uncached, counted as `hostname_not_unique` in `signed_put.skipped_puts_total`, and serves every request as usual. See [Shared storage](docs/SHARED_STORAGE.md#each-proxy-needs-its-own-hostname).

- A startup warning when the cache directory is on an NFS mount without `lookupcache=pos` (or `lookupcache=none`). It names the mount, and the proxy still starts. Without the option, a proxy can treat a peer's new files as absent. See [Mount requirements](docs/SHARED_STORAGE.md#mount-requirements).
- Prebuilt `s3-proxy` binaries for Linux on x86_64 and aarch64 (glibc 2.34 or newer), so a host needs no Rust toolchain. Each GitHub release from 3.0.0 carries them with a `SHA256SUMS` file and build provenance attestations. See [Binary portability](docs/GETTING_STARTED.md#binary-portability).
### Changed

- Previously, eviction found candidates by scanning every metadata file. It now picks candidates from a per-shard index, expired ranges first and then the largest, and starts within one `cache.shared_storage.consolidation_interval` of the cache passing a limit. See [Eviction flow](docs/EVICTION.md#eviction-flow) and [Triggers](docs/EVICTION.md#triggers).
- Previously, a config that omitted `cache.eviction_algorithm`, or set `"lru"`, evicted the least recently used range first. `tinylfu` is now the only algorithm, so a range read often but not recently is kept ahead of one read once, recently. `"lru"` still loads and logs one startup warning. See [Eviction](docs/EVICTION.md#eviction-algorithms).
- Previously, the write-cache size was a running counter that could drift, and on volumes written by 2.8 it usually overstated the write cache. Once every proxy on the volume runs 3.0.0, no 2.8 proxy has written to it for at least a day, and the proxies have checked every cache shard, it is recomputed from the cache's metadata and corrects itself. From then on, rolling back needs a fresh cache volume. See [Eviction](docs/EVICTION.md#which-computation-is-in-force) and [Upgrading](docs/UPGRADING.md#rolling-back-from-300).
- Previously, a GET that missed the cache was stored even when the cache was already at `max_cache_size`, so sustained miss traffic could grow the cache well past its limit. Once the cache reaches `max_cache_size`, a miss is now served from S3 and left uncached until eviction brings the total back below the limit, counted in `cache.read_fills_declined_max_cache_size_total`. The client gets the same response either way. See [Metrics reference](docs/METRICS_REFERENCE.md#the-max_cache_size-soft-stop-on-fills).
- A cache full of small objects stops caching writes at a published staged-range limit, and count-based eviction reclaims space so caching resumes on its own. Uploads always reach S3. See [Metrics reference](docs/METRICS_REFERENCE.md#the-staged-range-budget).
- The daily validation scan runs once a day for the whole fleet: a proxy skips its scan when another proxy completed one in the last 23 hours. Previously each proxy ran its own scan every day, one after another. The scan also removes cached HEAD responses for objects whose body was never cached. A proxy starting long after the last scan loads the saved size figure and asks for a scan, where it previously counted every cached object itself. An hourly pass recomputes the size figures eviction reads by listing and checking the size of the cached files on the cache volume. See [Shared storage](docs/SHARED_STORAGE.md#the-validation-scan) and [Eviction](docs/EVICTION.md#re-grounding-the-size-figures-the-triggers-read).
- Previously, `cache.shared_storage.lock_timeout` (default `60s`) did not control how long a metadata lock acquisition waited. It is renamed `lock_acquire_wait_budget`, defaults to `5s` and is honored: on expiry the request fails with a retryable error having written nothing. A value set under the old name still loads and becomes the budget. See [Configuration reference](docs/CONFIGURATION.md#metadata-lock-timing).
- Previously, a write through one spelling of an object key (`%20` or `+`, `%2F` or `/`) left the copy cached under another spelling in place, so a proxy could keep serving the old object. Cache keys now hold the object key in the spelling AWS SDKs send, so one object has one cache entry. Entries cached under another spelling become misses and age out. See [Cache internals](docs/CACHE_INTERNALS.md#object-key-spelling).
- The health and metrics listeners bind `127.0.0.1` when `bind_address` is omitted, as the dashboard already did, where they previously bound all interfaces. A check or scrape from another host needs `bind_address: "0.0.0.0"`.
- `/metrics` answers immediately and OTLP exports on schedule: metrics are collected in the background every `metrics.collection_interval` (default `60s`). Shared-volume figures can be up to one interval old, and a figure that cannot be read reports `null` where it previously reported `0`. See [Metrics reference](docs/METRICS_REFERENCE.md#metrics_collection).
- Previously, on a slow cache volume a PUT, UploadPart, multipart upload, DELETE, DeleteObjects or form POST could hold up the client's upload or wait for the cache after S3 had answered. Cache work now adds at most 1 second to a write's response (3 seconds for a DeleteObjects), and a streamed upload continues to S3 uncached after at most 5 seconds. Until a write's invalidation lands, the proxy that took it fetches that object from S3. When cache waits keep timing out, the proxy sends reads and writes straight to S3 until the volume answers again, shown by `cache.volume_stall_breaker_open`. See [Error handling](docs/ERROR_HANDLING.md#8-a-slow-cache-volume-on-the-write-path-bounded-waits).
- Multipart uploads are write-cached while the volume holds at most 5,000 in-progress entries; further uploads go to S3 uncached, counted as `multipart_tracking_full` in `signed_put.skipped_puts_total`. The size of in-progress parts is read once per `metrics.collection_interval`, and `cache.in_progress_part_bytes_age_secs` reports the figure's age. See [Metrics reference](docs/METRICS_REFERENCE.md#skipped_puts_total).
- `download_bandwidth.fleet.instance_staleness` defaults to `90s` instead of `30s`, so a proxy is counted in the fleet's bandwidth share for longer after its last update. See [Bandwidth QoS](docs/BANDWIDTH_QOS.md#fleet-sharing-cap--n).
- CompleteMultipartUpload is answered at most 250 ms after S3 answers, where it previously waited for the proxy to finish caching the object. A GET with more than one range is forwarded to S3 and answered as S3 answers it, where the proxy previously answered `501`.
- New range files use 64 KiB LZ4 blocks instead of 4 MiB, so highly compressible content takes more disk space and the reported cache size rises for the same data. Existing files still read. See [Compression](docs/COMPRESSION.md#block-size).
- `connection_pool.max_lifetime` (default `300s`) is now enforced, where it previously had no effect, so each pooled upstream connection is recycled about every five minutes. See [Connection pooling](docs/CONNECTION_POOLING.md#4a-maximum-lifetime).
- `cache.get_ttl` defaults to 1 day instead of about 10 years (`315360000s`), so an object changed in S3 without going through the proxy is seen within a day. This costs about one conditional GET per cached object per day when it is read, with no body transfer when the object is unchanged. A config that sets `get_ttl` is unaffected; to keep the old behavior, set `cache.get_ttl: "315360000s"`. See [Cache freshness](docs/CACHE_FRESHNESS.md#get-ttl-get_ttl).
- `health.check_interval` and `cache.initialization.parallel_scan`, `scan_timeout` and `progress_logging` (environment variables `PARALLEL_SCAN`, `SCAN_TIMEOUT`, `PROGRESS_LOGGING`; flags `--parallel-scan`, `--no-parallel-scan`, `--scan-timeout`, `--progress-logging`, `--no-progress-logging`) have never had an effect, public 2.8.4 included. 3.0.0 logs one startup warning naming each one set to a value other than its default, and no longer refuses to start over an out-of-range `scan_timeout`.

### Fixed

- Previously, after a PUT, CompleteMultipartUpload, DELETE, DeleteObjects or form POST upload was acknowledged, the proxy that took the write could keep serving the old object. This happened when two writes of one key landed close together, when a cache fill was in flight, or when the completion was signed in the query string. It now serves the new object. Other proxies sharing the volume can serve the old object from RAM for up to `cache.ram_cache_verification_interval` (1 second by default) for object data and `cache.metadata_cache.refresh_interval` (5 seconds by default) for HEAD answers. See [Caching](docs/CACHING.md#write-through-ordering).
- Previously, a RAM-tier hit, including a page-widened read, could return an old body under a newer object's headers until LRU eviction or a restart. RAM hits are now re-checked against shared metadata after `cache.ram_cache_verification_interval` (default `1s`), and `get_ttl` and `ram_cache_eligible` apply on every read path. See [Cache freshness](docs/CACHE_FRESHNESS.md#ram-tier-coherency-contract).
- Previously, a range served from a proxy's RAM cache did not count as a read for eviction, so the disk copy of a range read mostly from RAM aged as if unread and could be evicted ahead of colder ranges. It now counts as a read of the stored range it came from, the same as a disk read, including a hit on an object this proxy has filled but not yet written to the shared `.meta`. Each RAM hit adds one record to a 4,096-record queue that a single background task writes to the hit buffer. When the queue is full the record is dropped and counted in `cache_hit_buffer.ram_records_dropped_total`, so a flood of RAM hits costs bounded work.
- Previously, when an object changed in S3 while part of it was cached, or two proxies cached the same range from two versions, a response could join bytes of two versions. It could also serve one version's bytes under another's ETag or length. Cached bytes are now served only under the version they were cached for, and are otherwise fetched from S3; a response already streaming from the cache ends early with a connection error. Ranges cached before 3.0.0 are served as before. See [Metrics reference](docs/METRICS_REFERENCE.md#atomic_metadata).
- Previously, a client that sends `If-Match` on every ranged chunk (the CRT and Rust transfer managers, Mountpoint) made the proxy discard the cache entry it had just confirmed as current. The entry is now kept, so those clients get cache hits. See [Cache freshness](docs/CACHE_FRESHNESS.md#a-revalidation-responses-etag-decides-currency-not-its-status).
- Previously, some requests could be served from the cache past `get_ttl`. A `GET` sending `If-Match` with the cached ETag extended the entry each time. A request whose revalidation S3 answered with a `5xx` got a copy as old as its stored expiry allowed. A `HEAD` with a `Range` header followed `get_ttl` instead of `head_ttl`. Each now follows the key's current TTL.
- Previously, a conditional request could get a different answer from the one S3 gives. A client's own `If-None-Match` or `If-Modified-Since` could get a cached body where S3 answers `304`. A request with no precondition could get `412`. A failing `If-Match` on a range got a `412` without S3's error body. An `If-Range` naming an overwritten object's ETag could get `412` or part of the new object. These requests now get S3's answer.
- Previously, a `?partNumber=` GET was served from the cache under its stored expiry, even after `get_ttl` was lowered, and a conditional part GET got the cached part where S3 answers `412` or `304`. A `partNumber` outside 1 to 10,000 could return the whole object. Part GETs now follow `get_ttl`, conditional part GETs reach S3, and an out-of-range `partNumber` is forwarded to S3 uncached. See [Caching](docs/CACHING.md#operations-that-bypass-cache).
- Previously, a ranged SDK download whose cached data could not be served failed with `500`, `502` or `SignatureDoesNotMatch`. It is now answered from S3. See [Cache read paths](docs/CACHE_READ_PATHS.md#signed-range-requests).
- Previously, some signed requests failed with `403` through the proxy. These were a presigned URL that signs `Range`, `Cache-Control`, `Pragma` or `Via`, and a presigned GET the proxy had to complete from S3 part-way through. A request carrying one header on several lines, as the AWS SDK for Rust sends with GetObjectAttributes, failed too. These requests now reach S3 as the client signed them.
- Previously, with `connection_pool.ip_distribution_enabled` on (the default), a client sending a `Host` the upstream certificate does not cover could make other clients' correctly signed requests fail with `502 Bad Gateway`. Each request now connects using the hostname it targeted, so only that request fails. See [Connection pooling](docs/CONNECTION_POOLING.md#5-per-ip-pool-isolation).
- Previously, a virtual-hosted request for a bucket whose name contains a dot, which Mountpoint sends by default through an HTTP endpoint, could fail with `502 Bad Gateway`. The proxy now checks the upstream certificate against the S3 endpoint name, so the request is served. See [Connection pooling](docs/CONNECTION_POOLING.md#5-per-ip-pool-isolation).
- Previously, an OTLP endpoint with no path, including the default `http://localhost:4318`, exported to `/`, so the documented CloudWatch agent and OpenTelemetry Collector setups received nothing. It now exports to `/v1/metrics`. See [OTLP metrics](docs/OTLP_METRICS.md#enabling-otlp-metrics).
- Previously, the dashboard showed a write-cache limit of 10% of the cache size whatever `cache.write_cache_percent` was set to. It now shows the limit the proxy enforces.
- Previously, objects cached by a write-through PUT were served without their stored `Content-Type`, user metadata or other headers, and with the request's `Content-MD5`. They are now served with the headers they were written with.
- Previously, two proxies updating one object's cache metadata at the same time could overwrite each other's update, and eviction could delete an object rewritten after it was selected. Metadata updates no longer overwrite each other, and eviction skips an object rewritten after selection.
- Previously, overwriting or deleting a cached object left the cache size and object count too high until the next validation scan. They are now corrected when the write is applied. A write made while a validation scan is running can still be counted twice until the next scan.
- Previously, a read over 8 MiB, or a request waiting on another request's fetch of a changed object, was assembled in memory, so concurrent large reads could exhaust proxy memory. Both now stream. See [Cache freshness](docs/CACHE_FRESHNESS.md#scenario-3e-cached-data-too-large-to-assemble-in-memory).
- Previously, heavy concurrent writes or bulk deletes on the cache volume could stop a proxy serving requests, `/health` and `/metrics`. It now keeps serving.
- Previously, a host crash or storage write error could leave a cache entry that served incomplete data. Cache data and metadata are now flushed before they are published.
- Previously, after a proxy was killed or crashed, the next start on the same host discarded about the last 5 seconds of cache fills, so those objects were fetched from S3 again. They are now kept when the proxy restarts within 5 minutes.
- Previously, a cached range file that failed its integrity check stayed in the cache, so later reads kept refetching it or stopping part-way. The proxy now removes the damaged range when a read finds it, up to 16 a minute per proxy, and fetches it from S3 until it is gone. See [Metrics reference](docs/METRICS_REFERENCE.md#atomic_metadata).
- Previously, a range that a 2.8 proxy had cached from an S3 error reply could be served as object bytes. 3.0.0 detects such a range on read and fetches it from S3.
- Previously, a GET of an expired object could fetch it from S3 twice when its cache metadata had just been removed or had neither an ETag nor a Last-Modified. It is now fetched once.
- Previously, an access-log record could be lost while the logger was busy. It is now written, and `request_metrics.access_log_records_dropped` counts any that still cannot be.
- Previously, completing a multipart upload whose final or only part was zero bytes could cache the object with an invalid byte range. The proxy now does not cache such an upload; the upload to S3 is unchanged and later reads are fetched from S3.
- Previously, after an object changed size, a signed suffix range such as `Range: bytes=-N` could be cached at offsets computed from the object's old size. A later read of those offsets then got the wrong bytes. The proxy now caches a ranged response only when the byte range S3 returns starts and ends where the proxy expected from its cached copy, or ends earlier because the object ends there.
- Previously, when S3 answered a signed range request with the whole object, for example because the request's `If-Range` named an older version, the proxy could cache the whole object at the requested range's offsets. A later read of that range then got the wrong bytes. The proxy now caches such a response only when the requested range is the whole object.
- Previously, a range read under a prefix with page widening enabled, served before the proxy recorded the object's metadata, could report the end of the requested range as the object's size in its Content-Range header. It now reports the object's real size, or fetches the range from S3 when the size is not yet known.
- `cache.max_metadata_file_bytes` and `cache.metadata_io_concurrency` now take effect. Up to and including public 2.8.4 the proxy parsed both and always used 4 MiB and 32; a configured value now sets the size cap and the concurrency limit for range lookups in the disk cache, validation against HEAD, range invalidation, and the RAM-hit recorder's extent read. Every other `.meta` read uses neither, including the lookup that serves a GET or HEAD when an object's metadata is not in the RAM metadata cache, the HEAD-entry lookup, the RAM-hit ETag check, TTL refresh, the write cache, eviction and journal consolidation. A `max_metadata_file_bytes` below 64 KiB is raised to 64 KiB, and a `metadata_io_concurrency` of 0 to 1, each with a warning.
- Previously, the warnings about removed, ignored or remapped configuration fields never reached the application log, because the proxy loaded its configuration before it started logging. This was true up to and including public 2.8.4. Those warnings, and every other message logged while the configuration loads and the directory permissions are checked, are now written once logging starts, at the same level and with the same text.

### Security

- Previously, a `health.bind_address` or `metrics.bind_address` that was not an IP address, such as `localhost`, was ignored and the listener was published on every interface. The proxy now refuses to start and names the field. See [Configuration reference](docs/CONFIGURATION.md#health-check-configuration).
- Previously, the access log recorded the `Signature` and `AWSAccessKeyId` of a SigV2 presigned URL in full. They are now masked like their SigV4 counterparts. See [Access log format](docs/ACCESS_LOG_FORMAT.md).
- Previously, a GET or HEAD for a named object version (`?versionId=`) that also sent `Cache-Control: no-cache`, `Cache-Control: no-store` or `Pragma: no-cache` was cached under the object's own key. Later plain requests from any client then got that version. Versioned requests are now forwarded to S3 and never cached. See [Caching](docs/CACHING.md#versioned-request-handling).
- Previously, an open-ended `Range: bytes=N-` or suffix `Range: bytes=-N` for an object with no cached length was stored as the whole object. A later read of the start of the object got the bytes from offset `N`. A transfer manager sends a multipart download's last chunk this way. Such a response is now passed to the client and not cached, and [Upgrading](docs/UPGRADING.md#before-you-upgrade) names the one case where a cache volume written by an earlier release needs clearing.
- Previously, a client could send the proxy's internal `x-proxy-injected-if-match` or `x-proxy-injected-if-unmodified-since` header to have an object's cached ranges discarded and refetched, and receive the object where S3 answered `412`. The proxy now removes its internal headers from every client request.
- Previously, a key whose `get_ttl` is `"0s"` could still be answered from the cache without S3 evaluating the request, on a `?partNumber=` GET or a page-widened read, including one waiting on another request's fetch of the same page. Each now reaches S3.
- A bucket's cache entries are bound to the origin that cached them, AWS hostnames that are not S3 endpoints are not cached, and a forward-proxy request whose `Host` disagrees with its target is refused. Previously another AWS service's response, or one bucket's object under another bucket's key, could be cached and served. See [Caching](docs/CACHING.md#one-bucket-name-at-two-origins).
- Previously, with `server.tls.connect_allowlist` set, the destination policy applied to the port-80 listener but not to the TLS proxy listener's HTTP forwarding path. Both listeners now apply it.
- Requests with `response-*` header overrides, object subresources or unrecognized query parameters, and tagging, ACL, retention, legal-hold and copy PUTs, are not cached, so their responses are never served as the object. See [Caching](docs/CACHING.md#operations-that-bypass-cache).
- Updated `hickory-resolver`, which resolves S3 endpoint names, from 0.26.1 to 0.26.3 (GHSA-3w89-7rx5-hpwx, GHSA-6w6g-hm98-mhgm, GHSA-29q9-p769-j8gq, GHSA-67wc-6jq8-ghrc). No configuration change is needed.
- Updated `rustls` from 0.23.45 to 0.23.46 (RUSTSEC-2026-0346, RUSTSEC-2026-0347, RUSTSEC-2026-0348, RUSTSEC-2026-0349). This build does not use the features these advisories affect. No configuration change is needed.
- Updated `rustls-webpki`, which validates the certificates S3 presents, from 0.103.15 to 0.103.16 (RUSTSEC-2026-0382: certificate verification could accept distrusted intermediates). Updated the `webpki-roots` development dependency from 0.26.11 to 1.0.10 (RUSTSEC-2026-0381: the bundled roots trusted distrusted emSign intermediates). `webpki-roots` is used only by unit tests and is not in the shipped binary. No configuration change is needed.
- Previously, a `cache_rules.json` pattern containing a character that takes three or four bytes in UTF-8 made every GET and HEAD request fail by closing its connection once the rule was loaded. Examples are Chinese, Japanese or Korean text and emoji. Such patterns now load and match normally.
- Previously, a TLS client could send the HTTPS passthrough listener a server name containing line breaks and so add fabricated lines to the application log. The dashboard also did not escape quotes in log entries and error messages. The proxy now closes a connection whose server name contains a control character or a double quote without logging the name, and the dashboard escapes quotes.

### Deprecated
- `cache.max_metadata_file_bytes`. Leave it unset; the default cap of 4 MiB applies.

### Removed

- The periodic orphan sweep that re-attached unreferenced range files to metadata. Orphan cleanup removes such files instead, and the `orphan_recovery_enabled`, `orphan_recovery_interval`, `orphan_scan_timeout` and `orphan_max_per_cycle` fields are ignored; a config that sets them still loads, with one startup warning for any set to a non-default value.
- Configuration fields that had no effect; a config carrying them still loads. See [Configuration reference](docs/CONFIGURATION.md#configuration-methods).
- `/metrics` fields that always read zero, and OTLP series that were constant.
- `/metrics` fields that the proxy never updated: `cache.inconsistency_fixed_total`, `partial_write_cleanup_total`, `orphaned_files_cleaned_total`, `cache_write_failures_total`, `cache_operation_duration_ms` and `write_cache_hits`; `connection_pool.failed_connections` and `average_latency_ms`; and `atomic_metadata.stale_locks_detected`, `stale_locks_broken`, `orphaned_ranges_detected`, `orphaned_ranges_recovered`, `immediate_writes`, `journal_only_writes`, `hybrid_writes` and `write_mode_fallbacks`. The OTLP series `cache.write_cache_hits` goes with its field. Each read `0` on every proxy, so no alert or dashboard read real data from them.
